Decisions & Rationale

  • DECISION: logging and task tracking are hard rules; reporting stays default judgment. WHY: HTML report generation costs meaningfully more tokens than a log entry, so it should stay judgment-based (before merges, after code changes), while logs/tasks are cheap and are the actual context-recovery mechanism — skipping them loses information a later agent can't reconstruct.
  • DECISION: the task-signal nudge is a generic plans//specs/ path match, not tied to any specific companion skill (e.g. superpowers). WHY: monitor must stay independent of other plugins while working seamlessly with them — hard-coding a companion skill's directory convention would break that independence for projects not using it.
  • DECISION: commit this repo's own monitor/ data folder to git, removing the prior repo-specific "never commit" carve-out. WHY: explicit user request that the Host project use monitor exactly as a Guest project is expected to — logs and reports are the context-recovery mechanism, which only works if they're actually in the repo.
  • DECISION: switch from hand-edited settings.json plugin entries to the documented /plugin marketplace add + /plugin install commands. WHY: the hand-edit produced JSON that looked structurally correct (matching working plugins) but never registered monitor:* skills; the real commands write additional state a direct edit skips, confirmed by the settings.json diff after running them (reformatted key order and structure, not just value changes).
  • ARCHITECTURE: monitor/scripts/*.py stays a required project-local copy in both plugin and manual-install modes — never removed — because project-level hooks in .claude/settings.json cannot reliably resolve $CLAUDE_PLUGIN_ROOT outside the plugin's own hook manifest context, and monitor's self-containment principle requires monitor/ to keep working even if the plugin is later disabled.
