Summary

Implemented the already-approved pending-state-enforcement design: a new pending.py engine script backed by two real Claude Code hooks, installed via /monitor:init//monitor:update. 4 tasks, each built + task-reviewed clean (2 fix rounds along the way). The final whole-branch review found the hook-installation JSON used a schema that doesn't exist in real Claude Code (the feature would have shipped completely inert) plus a state-machine bug that could leave the warning stuck forever — both fixed in one dedicated fix wave, independently re-verified. Three smaller, bounded findings were parked rather than spending a second fix wave.

What Was Done

  • pending.py: tracks monitor/.pending.json (committed, per-branch state) — track/check for manual use, plus real hook entrypoints (hook-post-tool-use, hook-user-prompt-submit) speaking Claude Code's actual hook I/O contract.
  • logger.py/render_report.py clear the matching pending state exactly when a log or report completes (pinned to --lock-report, not the broader render_all(), to avoid clearing a genuinely-pending report during a plain init/update).
  • /monitor:init//monitor:update install the two hooks into a consumer project's .claude/settings.json; SKILL.md documents the mechanism.
  • Final review caught the hook JSON using a nonexistent command+args shape (verified against real Claude Code plugin schema-validation tooling) and wrong argparse ordering — both fixed to a single shell-string command with correct arg order.
  • Fixed a missing hookEventName key that would have silently dropped the injected warning.
  • Fixed the core "sticks forever" bug (2+ pending commits before a log) via a git-reachability-aware drain in clear_log(), plus anchored command classification (no more false positives on --dry-run/--abort), commit messages now sourced from real git history instead of the raw shell string, and commits touching only monitor/ no longer re-trigger the gate they themselves satisfy.

Decisions & Rationale

  • Soft Y/N gate, not a hard tool-call block — deliberate choice from the original design conversation, preserved through implementation.
  • Self-filtering in the hook script, not the settings.json matcher — confirmed the matcher field only filters by tool name, not command content, so pending.py reads tool_input.command itself.
  • clear_log()'s reachability-aware fallback over a new --last-commit-hash CLI flag — simpler, matches the "one /monitor:log per pending entry" usage pattern without adding surface area.
  • One fix wave for the final review, not a second — per the subagent-driven-development process cap; 3 residual findings were adjudicated and parked rather than looping further, since none were load-bearing (worst case is an extra reminder prompt, not data loss).
