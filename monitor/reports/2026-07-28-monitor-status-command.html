Summary

Added a new command, /monitor:status, designed via /superpowers:brainstorming with the schema and scope confirmed against the user before implementation: chat-only by default (no file ever written), backed by a fully deterministic Python script (status.py) that computes open tasks, recent log activity, pending-gate state, a slice of git history, and next steps — the last of these mechanically regex-extracted from NEXT:/GAPS:/ASSUMPTIONS: fields already recorded in prior log entries' --details text, never invented. The agent's only role is to read the JSON and phrase it in chat across four sections. Covered by 12 new unit tests and 2 new integration tests (96 total, all passing), plus a new dogfood step added to test-e2e's checklist for future end-to-end runs.

What Was Asked

Using /superpowers:writing-skills, create a monitor:status command for Guest projects that checks current tasks, logs, and a bit of git history, and tells the user the status directly in chat by default with no file created. The schema and script were to be designed via /superpowers:brainstorming first, producing a deterministic output covering what happened, what's currently being worked on, what's pending/queued, and next steps for the user — with unit, integration, and test-e2e coverage added for the feature.

What Was Done

  • Ran /superpowers:brainstorming through four rounds of clarifying questions (data scope, git scope, whether to fold in the pending-state gate, and how to derive "currently working on"/"next steps" without any live session-state file) — all resolved in favor of the fully deterministic option at each step, matching monitor's existing design philosophy of recording rather than guessing.
  • Implemented plugins/monitor/skills/monitor/scripts/status.py: reuses render_logs.parse_log and pending.open_tasks/load_pending rather than duplicating parsing logic, with --log-limit/--commit-limit flags (defaults 5/5) mirroring search.py's existing --limit pattern.
  • Added plugins/monitor/commands/status.md, instructing the agent to answer in four chat sections (What Happened / Currently Working On / Pending & Queued / Next Steps For You) and explicitly forbidding creating any file.
  • Documented the command and its schema in SKILL.md (a new "Status" section plus a command-table row and a "Common mistakes" entry), README.md, install-monitor.sh's echo output, and — since this propagates to every Guest project — the injected CLAUDE.md/AGENTS.md block in commands/init.md, mirrored into this repo's own CLAUDE.md/AGENTS.md per the self-host convention.
  • Wrote 12 unit tests (tests/unit/test_status.py) covering empty-project defaults, current-activity precedence (open task over log), open-task filtering, log-limit/commit-limit truncation, next-steps field extraction, pending-state mirroring, git uncommitted/untracked counting, and — specifically — that the command writes zero files.
  • Wrote 2 integration tests (tests/integration/test_status_flow.py) driving the real CLI subprocess entrypoint (not the Python function directly) against a project that had been through a real log+task+pending-commit flow, plus a pre-init failure case.
  • Added a new dogfood step to test-e2e's per-subagent checklist (now step 9, with the final report step renumbered to 10): run the status command mid-drill, verify its output actually reflects the subagent's own real task/log/next-steps content (not placeholder text), and confirm no file appeared under monitor/ from running it.
  • Bumped the plugin version 1.15.4 → 1.16.0 (a new command/feature, not a patch), updated the plugin manifest's description, synced the engine script into this repo's own monitor/scripts/, ran the full suite (96 pass) and the thought-leak scanner (clean) before committing.

Decisions & Rationale

  • DECISION: the script is 100% deterministic — no LLM judgment inside status.py itself; the agent only formats already-computed JSON into chat. WHY: confirmed explicitly with the user during brainstorming, and matches how monitor already treats logs/tasks/reports — record and extract mechanically, never guess, so the same project state always produces the same facts regardless of which agent or session reads it.
  • DECISION: "currently working on" prefers the most recently started open task over the most recent log entry; falls back to the log only if no task is open. WHY: a task represents a deliberately-started unit of work the user cares about tracking, which is a stronger signal of "what's actually being worked on right now" than an arbitrary log entry that could be a small mechanical aside.
  • DECISION: chat-only, zero files, enforced by a dedicated unit test (test_main_writes_no_files) rather than left to command-prompt discretion alone. WHY: the user was explicit that this must never create a file by default; a test that fails if a future edit accidentally adds a write is a stronger guarantee than a prose instruction alone.
  • DECISION: reuse render_logs.parse_log and pending.open_tasks/load_pending rather than writing new parsing logic. WHY: the operations-log and pending-state formats are already parsed correctly elsewhere; duplicating that logic would risk the two implementations drifting out of sync on edge cases (malformed blocks, escaped detail text) that the existing parsers already handle.
