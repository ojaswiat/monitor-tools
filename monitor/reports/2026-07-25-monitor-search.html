Summary

Added /monitor:search, a plain-text keyword search over monitor/logs/operations.mtr, plus an auto-captured last_commit_hash field on every log entry and a commit-range placeholder in generated reports. All five plan tasks landed, went through a whole-branch review, and the review's findings were fixed in a follow-up commit.

What Was Asked

Identify a real gap in monitor beyond the already-planned log/report enforcement work, then design and implement it: a way to search past log entries by keyword instead of paging through static HTML by hand, plus commit-hash traceability in both log entries and reports.

What Was Done

  • Added monitor_lib.git_last_commit(), mirroring the existing git_branch() — every log entry now auto-records the git HEAD short sha at logging time, no manual flag required.
  • Threaded last_commit_hash through logger.py's entry schema and render_logs.py's parser and card renderer.
  • Added search.py: filters operations.mtr by a case-insensitive substring query plus optional --branch/--status/--level, printing plain-text matches.
  • Added the /monitor:search command and registered it in SKILL.md, init.md's injected command table, and the root CLAUDE.md script list.
  • Wired the report template's existing (previously unused) {{ commit }} placeholder to a first..last short-sha range, documented in report.md and record.md.
  • Bumped the plugin to 1.10.0.
  • Ran a whole-branch review after all tasks landed and fixed every finding in one follow-up commit (README entry, a misleading commit-range claim, a --limit 0 bug, stale command lists elsewhere in the docs, a missing range-command example, and hardcoded status/level choices that should read from the schema).
  • Dogfooded the result: installed and initialised monitor on this repo itself, logged this branch's own milestones through the shipped logger.py, and ran search.py against the real log it produced.

Decisions & Rationale

  • Auto-capture over a manual --set commit=<sha> flag. A manual flag can be forgotten by the agent, and never applies to log entries a user triggers by hand. Auto-capture (mirroring how branch already works) closes that gap unconditionally.
  • Plain-text search output, no HTML results page. A search result is different every time it's run, while every other monitor page is static and pre-built — generating one here would be extra work that's stale on arrival.
  • first..last commit range for reports, not a single sha or a full comma-separated list — shows the whole span a report covers in one glance, the same notation git itself uses for ranges; a single sha silently drops multi-commit reports, a full list gets unreadable past a handful of commits.
  • No new automated test suite for this feature — standing project decision (confirmed by the project owner) given the engine's small, stdlib-only scope; verification here is a live run against a real log, not a mocked one.

Risks

  • Log entries written before this change have no last_commit_hash — they render without a commit chip rather than a wrong one, but older history stays unsearchable by commit.
  • The commit-range fill for reports is still agent-judgment at authoring time (determining "first commit unique to this branch"), not mechanically computed — a careless agent could still get the range wrong.

Gaps & Assumptions

  • No automated regression test guards search.py or the new schema field — verification is manual, per this project's standing no-test-suite decision.
  • Assumes every consumer project's git history has at least one commit at logging time; git_last_commit() returns "" gracefully otherwise (verified via git_branch()'s existing contract, which it mirrors).
