git log --oneline main..feat/upgrade-to-app

A parallel branch replaces the entire engine main is currently running: SQLite log store (db.py), a fixed static app shell + app.js renderer, migrate.py for pre-app installs, and a structured report.py writer — plugin.json already bumped to 2.0.0 there. main is still on the old profile.json/HTML-template architecture at 1.6.0.

Consequence: the two branches are diverging documentation and behavior. This session's own doc fix (removing the stale "ui-ux-pro-max designs the palette" framing) duplicates work already done correctly on the branch in commit d51700c — effort spent on main that the branch had already solved, and a merge will need manual reconciliation of both fixes.
Recommenddecide whether feat/upgrade-to-app replaces main's architecture or is abandoned — an unmerged, fully-versioned rewrite left indefinitely is the single biggest source of future inconsistency here.

F-03 clean.py regenerates Reports index + Dashboard with no branch, blanking the masthead chip MEDIUM
plugins/monitor/skills/monitor/scripts/clean.py:67-68
66    profile = mlib.load_profile(root)
67    render_report.render_reports_index(profile, kept, root)
68    render_report.render_dashboard(profile, len(kept), root)
Failure scenario: run /monitor:clean-reports 2 inside any git repo. render_reports_index()/render_dashboard() both default to branch="" when not passed. Every other caller (render_report.render_all()) passes mlib.git_branch(root) explicitly — clean.py is the one path that doesn't. The Dashboard and Reports index masthead chip now reads "no branch" even though the project is on a real branch, until the next full render_report.py run overwrites it.
Fixpass branch=mlib.git_branch(root) into both calls, same as render_all() does.

F-07 Logs page status filter depends on CSS :has() with no fallback INFO
plugins/monitor/skills/monitor/scripts/monitor_lib.py:210
210  body:has(#f-success:checked) .logcard:not(.success), … { display: none; }
On a browser without :has() support (pre-2023 Firefox/Safari/Chrome), the filter pills render, look interactive, and toggle their own active state — but nothing in the log list actually filters. No script and no graceful @supports fallback message.
Recommendlow priority given target browsers are current, but worth a note since the engine's stated principle is "no <script>, self-contained" — an @supports not selector(:has(a)) rule hiding the filter entirely would be an honest degrade.
